---
title: "Row Level Security"
description: "How Kairo uses PostgreSQL Row Level Security on Supabase to ensure coders only see their own data and Team Leaders see their clan."
---

Row Level Security (RLS) is a PostgreSQL feature that enforces data access rules at the database layer. Every query — regardless of where it originates — is automatically filtered by the active user's identity and role. On Supabase, RLS integrates directly with the `auth.uid()` and `auth.jwt()` functions, making it the primary security boundary for the Kairo API.

<Info>
  RLS is enabled on **all 14 tables**. If a policy does not explicitly permit
  an operation, the database returns zero rows (for SELECT) or raises a
  permission error (for INSERT / UPDATE / DELETE).
</Info>

## How it works

Kairo uses two mechanisms to identify the current user:

| Function             | Returns                          | Used for                                |
| -------------------- | -------------------------------- | --------------------------------------- |
| `auth.uid()`         | UUID of the authenticated user   | Matching rows owned by the current user |
| `auth.jwt()->>'role'`| Role claim from the JWT token    | Granting elevated access to TL users   |

The general access pattern across all tables follows these rules:

- **Coders** can read and write only their own rows (those where `coder_id = auth.uid()::int`).
- **Team Leaders** can read all rows (via `auth.jwt()->>'role' = 'tl'`).
- **Write access** is restricted: coders can update their own progress; only TLs can create plans and activities.

---

## Enabling RLS

Before any policies take effect, RLS must be enabled on each table:

```sql
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE soft_skills_assessment ENABLE ROW LEVEL SECURITY;
ALTER TABLE modules ENABLE ROW LEVEL SECURITY;
ALTER TABLE moodle_progress ENABLE ROW LEVEL SECURITY;
ALTER TABLE topics ENABLE ROW LEVEL SECURITY;
ALTER TABLE coder_struggling_topics ENABLE ROW LEVEL SECURITY;
ALTER TABLE complementary_plans ENABLE ROW LEVEL SECURITY;
ALTER TABLE plan_activities ENABLE ROW LEVEL SECURITY;
ALTER TABLE activity_progress ENABLE ROW LEVEL SECURITY;
ALTER TABLE evidence_submissions ENABLE ROW LEVEL SECURITY;
ALTER TABLE tl_feedback ENABLE ROW LEVEL SECURITY;
ALTER TABLE risk_flags ENABLE ROW LEVEL SECURITY;
ALTER TABLE ai_reports ENABLE ROW LEVEL SECURITY;
ALTER TABLE ai_generation_log ENABLE ROW LEVEL SECURITY;
```

## Policies by table

<AccordionGroup>

  <Accordion title="users">
    | Policy name         | Operation | Rule                                              |
    | ------------------- | --------- | ------------------------------------------------- |
    | `users_own_profile` | SELECT    | `id = auth.uid()::int`                            |
    | `users_tl_sees_all` | SELECT    | `auth.jwt()->>'role' = 'tl' OR id = auth.uid()::int` |
    | `users_edit_own`    | UPDATE    | `id = auth.uid()::int`                            |

    ```sql
    CREATE POLICY "users_own_profile"
      ON users FOR SELECT
      USING (id = auth.uid()::int);

    CREATE POLICY "users_tl_sees_all"
      ON users FOR SELECT
      USING (auth.jwt()->>'role' = 'tl' OR id = auth.uid()::int);

    CREATE POLICY "users_edit_own"
      ON users FOR UPDATE
      USING (id = auth.uid()::int)
      WITH CHECK (id = auth.uid()::int);
    ```

    <Note>The UPDATE policy does not restrict which columns can be changed. Application logic is responsible for preventing coders from modifying their own `role`.</Note>
  </Accordion>

  <Accordion title="tl_feedback">
    The most complex set of policies. Coders receive feedback; TLs send it. Both can update the same rows for different reasons (TL edits content; coder marks as read).

    | Policy name                | Operation | Who          | Rule                                                      |
    | -------------------------- | --------- | ------------ | --------------------------------------------------------- |
    | `feedback_own_feedback`    | SELECT    | Coder        | `coder_id = auth.uid()::int`                              |
    | `feedback_tl_sends`        | SELECT    | TL           | `tl_id = auth.uid()::int OR role = 'tl'`                  |
    | `feedback_tl_create`       | INSERT    | TL only      | `role = 'tl' AND tl_id = auth.uid()::int`                 |
    | `feedback_tl_edit`         | UPDATE    | TL only      | `tl_id = auth.uid()::int AND role = 'tl'`                 |
    | `feedback_coder_mark_read` | UPDATE    | Coder only   | `coder_id = auth.uid()::int AND role = 'coder'`           |

    ```sql
    CREATE POLICY "feedback_own_feedback"
      ON tl_feedback FOR SELECT
      USING (coder_id = auth.uid()::int);

    CREATE POLICY "feedback_tl_sends"
      ON tl_feedback FOR SELECT
      USING (tl_id = auth.uid()::int OR auth.jwt()->>'role' = 'tl');

    CREATE POLICY "feedback_tl_create"
      ON tl_feedback FOR INSERT
      WITH CHECK (auth.jwt()->>'role' = 'tl' AND tl_id = auth.uid()::int);

    CREATE POLICY "feedback_tl_edit"
      ON tl_feedback FOR UPDATE
      USING (tl_id = auth.uid()::int AND auth.jwt()->>'role' = 'tl');

    -- Coders can flip is_read = true but cannot edit other fields
    CREATE POLICY "feedback_coder_mark_read"
      ON tl_feedback FOR UPDATE
      USING (coder_id = auth.uid()::int AND auth.jwt()->>'role' = 'coder');
    ```

    <Tip>
      The `feedback_coder_mark_read` policy allows coders to mark a message as
      read. Application code should ensure coders only update `is_read` and not
      other columns.
    </Tip>
  </Accordion>

## Troubleshooting

**`permission denied` on a table**

The current user's role or `uid()` does not match any policy USING clause for that operation. Check:
1. The user's `role` value in the `users` table matches the JWT claim.
2. The row's ownership column (`coder_id`, `tl_id`, etc.) matches `auth.uid()::int`.
3. RLS is enabled and the correct policy file has been applied.

**Coder can see another coder's data**

Verify the policy uses `USING` (not just `WITH CHECK`) so it filters reads, not just writes. Also confirm the Supabase JWT contains the correct `role` claim.

**TL cannot see any data**

The JWT role claim may be missing or set to `'coder'`. In Supabase, this claim is typically set in the auth metadata or via a custom JWT hook. Verify with:

```sql
SELECT auth.jwt()->>'role';
```
